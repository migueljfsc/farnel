# Farnel v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A usable first version of Farnel: a Cloudflare Worker that serves a web UI and a stateless MCP server over one D1 database, protected by Cloudflare Access, deployed from `main`.

**Architecture:** One Worker. Static SPA from `dist/` (React); `/api/*` is a JSON API for the UI; `/mcp` is a stateless MCP server (`createMcpHandler`) that claude.ai uses as a custom connector. Both surfaces call the same service layer (`worker/lib/service/*`), which loads facts from D1 and applies pure rules (`worker/lib/rules.ts`). Access protects the hostname at the edge; the Worker verifies the Access JWT again.

**Tech Stack:** pnpm 11.9.0, Node ≥ 22.12, TypeScript strict, React 19, Vite 8, Tailwind v4, zod 4, Vitest 5 (+ `@cloudflare/vitest-plugin`), wrangler 4, `agents` + `@modelcontextprotocol/server`, `jose`, OpenTofu ~1.11 with the Cloudflare provider ~5.0, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-22-farnel-design.md`

## Global Constraints

- Code, UI copy, docs, comments and commit messages in English.
- Comments state what code does when non-obvious; no narration of history or of this plan.
- Mirror `../coutada` (sibling repo) for tooling and structure; strip coutada-specific comments, decisions references (`Dn`, `pb-Dn`) and features (Turnstile, Resend, sessions, Durable Objects, service worker, i18n).
- Dependencies: only those listed in Task 1. Exact versions must satisfy pnpm's minimum release age; `@modelcontextprotocol/server` is pinned to the exact version the installed `agents` release declares as its peer.
- The name `farnel` appears only in: `package.json` `name`, `wrangler.jsonc` `name`/route/D1 binding name, `infrastructure/.../variables.tf` `project_name` default and `backend.tf` key, the deploy workflow's environment URL and D1 command, and `src/lib/app.ts` `APP_NAME`. README lists these.
- Dates are `YYYY-MM-DD` strings in `Europe/Lisbon`; weeks start Monday. Money is integer cents.
- Ingredient price: `price_cents` is the price of 1000 g, 1000 ml, or 1 `un`.
- A portion is one person's serving; a meal consumes 2 portions.
- Every response goes through `secured()`; every JSON body is read with `readJson()`.
- Errors are machine codes (`{ "error": "code" }`), never sentences.
- Run `pre-commit run --all-files` before every commit; Conventional Commits. Push to `main` is allowed.

## Review Focus

1. **Two cookings in one plan covering the same meal (date + slot), or a meal already covered by another week's plan** → `save_plan` rejects with `meal_taken`; the DB never holds two cookings for one meal. Test in Task 5.
2. **Midnight in Lisbon vs. UTC** (e.g. `2026-03-29T23:30:00Z` is already the 30th in Lisbon after the DST switch) → "today" and week boundaries use Lisbon dates. Test in Task 3.
3. **Ingredient names differing only in case, accents or spacing** ("Grão", " grao ") → `add_dish` reuses the existing ingredient instead of creating a duplicate with `unknown` statuses. Test in Task 4.
4. **A person edits a dish's ingredients after it was validated, adding an ingredient that is `unknown`** → the dish stays `validated` but drops out of candidates (rule 1) until decided; it is not silently plannable. Test in Task 4.
5. **`save_plan` called twice for the same week after the first cooking's date has passed** → second call is rejected with `plan_locked`, history unchanged. Test in Task 5.

### Task 3: Time, names and pure rules

**Files:**
- Create: `worker/lib/time.ts`, `worker/lib/names.ts`, `worker/lib/rules.ts`
- Test: `worker/lib/time.test.ts`, `worker/lib/names.test.ts`, `worker/lib/rules.test.ts`

**Interfaces:**
- Produces:
  - `todayLisbon(now: Date): string`; `isMonday(date: string): boolean`; `weekStartOf(date: string): string`; `addDays(date: string, days: number): string`; `daysBetween(a: string, b: string): number` (b − a).
  - `nameKey(name: string): string` — NFD, strip combining marks, lowercase, trim, collapse inner whitespace.
  - `lineCostCents(quantity: number, unit: Unit, priceCents: number | null): number | null` — `null` when price is null; `round(quantity * priceCents / (unit === 'un' ? 1 : 1000))`.
  - `type DishFacts = { id: number; status: DishStatus; portions: number; repeatIntervalDays: number; lastCooked: string | null; ingredients: { quantity: number; unit: Unit; priceCents: number | null; statuses: Record<number, RestrictionStatus> }[] }`
  - `type RuleCode = 'not_validated' | 'restricted' | 'cooldown'`
  - `eligibility(dish: DishFacts, hardRestrictionIds: number[], onDate: string): RuleCode[]` — empty array = eligible. `restricted` when any ingredient's status for any hard id is not `'safe'` (missing counts as `unknown`). `cooldown` when `lastCooked !== null && addDays(lastCooked, repeatIntervalDays) > onDate`.
  - `costPerPortionCents(dish: DishFacts): { cents: number; missingPrice: boolean }`.
  - `type PlanInput = { weekStart: string; notes?: string; cookings: { dishId: number; cookDate: string; portions: number; meals: { date: string; slot: Slot }[] }[] }`
  - `type PlanErrorCode = RuleCode | 'week_start_not_monday' | 'unknown_dish' | 'duplicate_dish' | 'empty_meals' | 'portions' | 'date_out_of_week' | 'meal_before_cook' | 'in_past' | 'meal_taken' | 'plan_locked'`
  - `type PlanError = { code: PlanErrorCode; cooking?: number; dishId?: number }` (`cooking` = index in input)
  - `validatePlan(input: PlanInput, facts: { dishes: Map<number, DishFacts>; hardRestrictionIds: number[]; today: string; takenMeals: Set<string> }): PlanError[]` — `takenMeals` holds `"date|slot"` of meals in *other* weeks' plans. Eligibility is checked against `onDate = min(cookDate)` of the input. Order of checks per cooking: unknown_dish, duplicate_dish, empty_meals, portions (`portions < meals.length * 2`), date_out_of_week (cook or meal date outside `[weekStart, weekStart+6]`), meal_before_cook, in_past (`cookDate < today`), meal_taken (within input or in `takenMeals`), then eligibility codes.
